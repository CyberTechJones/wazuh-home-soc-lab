# SOC Investigation Playbooks

## Overview

This directory contains repeatable investigation procedures developed from the detection scenarios completed in my Wazuh home SOC lab.

The detection scenarios document specific controlled tests and their results. These playbooks provide reusable workflows for investigating similar alerts, evaluating available evidence, determining scope, and assigning an appropriate disposition.

## Investigation Methodology

Each playbook will follow a consistent workflow:

1. Review the alert metadata.
2. Validate the underlying event.
3. Identify the affected asset and user.
4. Determine the scope and timeline.
5. Review related endpoint and SIEM telemetry.
6. Evaluate legitimate explanations.
7. Identify evidence limitations.
8. Assign severity and confidence.
9. Determine whether escalation is required.
10. Document the final disposition and response recommendations.

Provides a workflow for investigating Sysmon Process Create Event ID `1`, including process image, command line, parent process, user context, integrity level, hashes, and MITRE ATT&CK mappings.

## Alert Classification

- **Event:** A structured record describing observed system activity.
- **Alert:** An event or group of events that matched detection logic.
- **True positive:** Detection logic correctly identified the observed behavior.
- **Authorized benign true positive:** The behavior was correctly detected but intentionally generated during an authorized test.
- **False positive:** Benign activity was incorrectly classified by the detection logic.
- **Suspicious activity:** Activity requiring additional investigation because the available evidence is inconclusive.
- **Incident:** Validated unauthorized activity requiring response or escalation.

## Severity Framework

- **Informational:** Expected or authorized activity with no meaningful security risk.
- **Low:** Activity requiring analyst review but presenting limited risk.
- **Medium:** Suspicious or unexplained activity requiring further investigation.
- **High:** Evidence strongly supports unauthorized or harmful activity.
- **Critical:** Confirmed compromise with significant operational or security impact.

## Confidence Framework

- **Low:** Evidence is limited, incomplete, or conflicting.
- **Medium:** Several indicators support the conclusion, but questions remain.
- **High:** Endpoint and centralized evidence are consistent and directly support the conclusion.

## Evidence Standards

Investigations may use:

- Wazuh rule IDs, descriptions, and levels
- Windows Security events
- Sysmon events
- Process and command-line information
- Parent-child process relationships
- Authentication details
- File paths and hashes
- File Integrity Monitoring events
- Event timelines
- MITRE ATT&CK mappings
- Final alert dispositions

Analysts should distinguish between:

- What the evidence proves
- What the evidence suggests
- What the evidence does not establish

## Evidence Handling

Before evidence is published:

- Passwords, credentials, tokens, keys, and enrollment information are excluded.
- IP and MAC addresses are redacted when unnecessary.
- Personal identifiers are removed when they do not add investigative value.
- Screenshots contain only evidence relevant to the conclusion.
- Unredacted evidence remains outside the public repository.
- Claims remain limited to what the available evidence supports.
