# General Alert Triage Playbook

## Purpose

Provide a repeatable workflow for reviewing, validating, classifying, and documenting alerts generated by Wazuh.

This playbook applies to authentication, process, PowerShell, Sysmon, and File Integrity Monitoring alerts. Specialized playbooks may add alert-specific investigation steps.

## Scope

Use this playbook for alerts involving monitored assets within the authorized home SOC lab:

- **SIEM-01:** Wazuh Security Information and Event Management platform
- **ENDPOINT-01:** Monitored Windows 11 endpoint
- **TEST-01:** Kali Linux testing and monitored Linux system

This playbook supports initial alert review, evidence validation, scope determination, severity assessment, escalation decisions, and final disposition.

## Trigger Conditions

Use this playbook when:

- A new Wazuh alert requires analyst review.
- The underlying activity has not been classified.
- The affected asset, account, process, or file requires validation.
- The alert requires severity and confidence assessment.
- The alert may be related to other events.
- It is unclear whether escalation or response action is necessary.

## Expected Outcomes

The triage process should produce:

- A validated understanding of the underlying event
- An identified asset, user, process, or file
- A documented event timeline
- A defined investigation scope
- An assessment of legitimate explanations
- Documented evidence limitations
- A severity and confidence rating
- A final alert disposition
- An escalation or closure decision
- Proportionate response recommendations

## Investigation Inputs

Before beginning, collect the available alert information:

- Alert timestamp
- Wazuh rule ID
- Rule description
- Rule level
- Agent name and ID
- Affected hostname
- Affected user or account
- Windows or Sysmon Event ID
- Process image and command line
- Parent process
- File path and hashes
- Source and destination information
- MITRE ATT&CK mapping, when present

If a field is unavailable, record it as `Not available` rather than estimating it.

### 5. Determine the Scope

Search for:

- Repeated alerts involving the same user
- Similar events on the same endpoint
- Similar activity on other endpoints
- Additional processes launched by the same parent
- Related file or registry changes
- Related authentication activity
- Events outside the expected test window
- Successful activity following failed attempts
- Additional alerts using the same Wazuh rule

Classify the scope:

- **Isolated:** One event on one asset
- **Repeated:** Multiple related events on one asset
- **Distributed:** Similar activity across multiple assets or accounts
- **Unknown:** Available evidence is insufficient to determine scope

### 9. Assign Severity

Assign severity based on the observed risk, not only the Wazuh rule level.

#### Informational

Expected or authorized activity with no meaningful security risk.

Examples:

- Authorized telemetry validation
- Benign activity collected without an alert
- Expected system behavior

#### Low

An alert requires analyst review but presents limited risk.

Examples:

- A small number of failed logons
- An authorized FIM change
- Controlled PowerShell execution

#### Medium

Activity is suspicious or unexplained, but compromise is not confirmed.

Examples:

- Repeated authentication failures from an unexpected source
- Unapproved PowerShell discovery activity
- Unexpected changes to monitored application files

#### High

Evidence strongly supports unauthorized or harmful activity.

Examples:

- Confirmed credential compromise
- Malicious file modification
- Unauthorized persistence
- Suspicious process execution with supporting compromise indicators

#### Critical

Confirmed compromise creates significant operational or security impact.

Examples:

- Ransomware activity
- Destructive activity across multiple systems
- Widespread credential compromise
- Active data exfiltration

Record:

- **Assigned severity:** `[INFORMATIONAL/LOW/MEDIUM/HIGH/CRITICAL]`
- **Reasoning:** `[ENTER EVIDENCE-BASED JUSTIFICATION]`

### 10. Assign Confidence

#### Low Confidence

Evidence is incomplete, conflicting, or limited to one weak indicator.

#### Medium Confidence

Multiple indicators support the conclusion, but important questions remain.

#### High Confidence

Endpoint and centralized evidence are consistent, the timeline is established, and the conclusion is directly supported.

Record:

- **Assigned confidence:** `[LOW/MEDIUM/HIGH]`

### 11. Determine the Final Disposition

Choose the disposition that best matches the evidence:

- **Authorized benign activity:** Authorized activity was observed but did not generate an alert.
- **Authorized benign true positive:** Detection logic correctly identified authorized test behavior.
- **False positive:** Detection logic incorrectly classified benign activity.
- **Suspicious activity:** Evidence requires further investigation.
- **Confirmed incident:** Evidence supports unauthorized activity requiring response.
- **Insufficient evidence:** Available telemetry does not support a reliable conclusion.

## Escalation Criteria

Escalate when one or more of the following conditions apply:

- The activity was not authorized.
- The affected user, account, or endpoint cannot be validated.
- Evidence suggests successful unauthorized access.
- Similar activity affects multiple accounts or endpoints.
- Activity continues after the initial alert.
- A suspicious process launches additional processes.
- PowerShell contains encoded, obfuscated, or unexplained commands.
- File changes affect critical Windows or application paths.
- Evidence indicates persistence, credential access, lateral movement, or data access.
- The activity warrants Medium, High, or Critical severity.
- A reasonable benign explanation cannot be supported.

Escalation should be based on observed evidence rather than the Wazuh rule level alone.

## Closure Criteria

Close the alert only when:

- The underlying event has been validated.
- The affected asset and account have been identified.
- The event timeline has been reviewed.
- The activity scope has been evaluated.
- Related events and alerts have been reviewed.
- Legitimate explanations have been considered.
- Evidence limitations have been documented.
- Severity and confidence have been assigned.
- The final disposition is supported by evidence.
- Required response actions have been completed or escalated.

## Evidence Handling

Before publishing investigation evidence:

- Remove passwords, tokens, keys, and enrollment information.
- Redact IP and MAC addresses when they do not add investigative value.
- Remove personal identifiers that do not support the conclusion.
- Preserve unredacted originals outside the public repository.
- Keep screenshots focused on relevant evidence.
- Verify that screenshots match the documented event and timestamp.
- Limit conclusions to facts supported by the displayed evidence.
